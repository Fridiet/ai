# 로컬 DB 세부 식재료 동기화

2026-09-12 사용자 승인 후 localhost의 `Fridiet` DB에 적용했다. 스키마 변경은 없다.

## 적용 결과

- 재료 마스터 404 → 610개: 206개 추가. 기존 ID·이름·속성은 보존.
- 별칭 422개 추가, 285개를 세부 재료에 재연결. 사전에 없는 별칭은 보존.
- 카탈로그 레시피 961개 및 레시피 ID 유지. 761개 레시피의 재료 연결 갱신.
- 연결 행 1,743개 추가, 1,498개 제거, 61개 수정. 변경 없는 연결 ID 유지.
- 기존 재고·사용자 저장 레시피·행동 기록 등 나머지 31개 테이블의 내용 해시가 동일함을 확인.
- 재실행 dry-run의 추가 변경 0건. 전체 테스트 222개 통과.

원본 JSON의 소수 수량은 기존 DB의 `DECIMAL(10,2)` 정밀도로 저장된다. 최초 적용 시 검증이 이 차이를 발견하여 트랜잭션이 롤백되었고, 저장 정밀도에 맞춰 비교하도록 수정 후 다시 적용했다. AI JSON의 정밀도는 변경하지 않았다.

## 실행

AI 폴더에서 아래 명령을 실행한다. 기본값은 DB를 수정하지 않는 dry-run이다.

```powershell
.\.venv\Scripts\python.exe -m scripts.sync_specificity_database
.\.venv\Scripts\python.exe -m scripts.sync_specificity_database --apply
```

접속 정보는 기존 개발용 설정 로더를 사용하며 자격 증명을 출력하지 않는다. 원격 호스트는 거부한다. 카탈로그의 출처 ID와 이름이 로컬 데이터셋과 일치하지 않거나, 카탈로그 재료 연결 행을 다른 테이블이 외래키로 참조하면 적용을 중단한다.

변경 대상 3개 테이블의 적용 직전 백업과 결과는 gitignored 경로 `output/ingredient_specificity/database/`에 저장된다. 백업은 참조 데이터 JSON이며 전체 DB 덤프/자동 복구 도구는 아니다. 적용 중 검증 실패 시 전체 변경이 롤백된다. 운영 중 다른 사용자의 쓰기와 동시에 실행하지 않는 것이 좋다.

## 보존한 사항과 한계

- 기존 재고에 단순히 `버섯`으로 저장된 데이터는 팽이버섯 등으로 추정 변경하지 않았다.
- 사용자 저장 레시피는 과거 스냅샷이므로 수정하지 않았다. 과거 저장본에는 넓은 재료명이 남을 수 있다.
- 카탈로그의 일반 `버섯` 3건은 세부 종류를 확정할 근거가 없어 그대로 유지한다.
- 카탈로그 본문·영양·출처 정보는 변경하지 않고 재료 연결만 동기화했다.
- 이 작업은 OCR 텍스트 인식 자체의 모든 오류를 해결하는 작업은 아니다.
- 프론트엔드·백엔드 소스 수정, 커밋, 원격 푸시는 하지 않았다.

# 추가 제공 영수증: 사용 원칙과 초기 점검

사용자가 제공한 `C:/Users/your-user/Downloads/train/train/images/`에서 이미지 464장을 확인했다.

- 이미지 내용·라벨을 학습에 사용하기 전에 분할 파일을 고정했다.
- SHA-256 동일성 및 dHash 거리 6 이내의 보수적 연결 그룹으로 기존 156장/시연 사진과 분리했다.
- 신규 개발용 152장, 기존 자료와 같거나 유사한 그룹 282장, 고정 평가용 30장(24그룹).
- 유사 그룹 282장이 모두 동일 영수증이라는 뜻은 아니다. 비슷한 영수증 양식도 묶일 수 있어 보수적으로 평가에서 제외했다. 반대로 이 방법이 모든 잘라내기·회전 중복을 검출한다는 보장도 없다.
- 현재 어떤 이미지도 학습 정답으로 승인하지 않았다. `train`이라는 원본 폴더명은 이번 실험의 역할과 별개다.
- 평가용 30장의 내용은 아직 검토하지 않았다. 개발 중 해당 이미지/라벨을 열어 튜닝하지 않는다.
- 개발용 IMG00001의 라벨은 클래스 ID와 정규화 사각형 좌표의 다섯 열이다. 텍스트 전사나 표준 재료명 정답은 아니다. 클래스 정의 파일은 제공 폴더 검색에서 찾지 못했다.
- 마트 외 배달 영수증도 있어 개발용 이미지의 매장 유형과 구매 식품을 별도로 확인해야 한다.

분할: `output/new_receipts/partition.json` (재실행 시 기존 분할 덮어쓰기 거부)

개발용 OCR 수집: `python -m scripts.prepare_new_receipt_snapshots --limit 12`

`--limit`을 빼면 신규 개발용 152장을 처리한다. 완료된 캐시는 재사용하며 실패 파일은 다음 실행에서 재시도한다. 원본 사진은 수정하지 않고 외부 서비스로 보내지 않는다. 로컬 `/ocr/raw`만 호출하며 DB에는 저장하지 않는다. 결과와 준비 상태는 gitignored `output/new_receipts/`에 저장한다.

새 데이터 기반 최종 정확도는 아직 측정하지 않았다. 라벨 정합성·영수증 유형·누수 여부 확인 후 고정 평가에서 별도로 보고해야 한다.

## 개발 진행

아래 진행 기록의 장수와 수치는 각 시점의 기록이다. 최신 주석 상태는 문서 마지막의 11장 평가를 참조한다.

신규 개발용 80장의 OCR 수집을 완료했다(평가용 제외, 수집 실패 0건). 원본 대조한 마트 영수증 5장의 주석 초안을 `evaluation/new_receipts_development.json`에 작성했다. 식품 13행 중 이름 확정 주석은 12행이며 한 글자 인쇄가 모호한 1행은 정답을 보류했다. 건강 보충제는 일반 재료 평가에서 제외하되 비식품 정답으로 단정하지 않았다. 신규 폴더에는 카페·외식 등도 섞여 있어 수집 장수를 마트 영수증 정답 장수로 해석하지 않는다.

`python -m scripts.evaluate_new_receipts`로 고정 평가용 이미지가 섞이지 않았는지 검사하고 개발용 평가를 실행한다. 결과는 `output/new_receipts/evaluation.json`. 현재 이름 일치 9건, 구매 수량 일치 9건, 두 항목 동시 일치 7건이다. 사람이 검증한 독립 성능이 아니다.

- 명시적인 식빵/샐러드/미네랄워터 접미사 처리. 생수의 표준명은 기존 사전에 맞춰 `물` 사용.

## 가격 열을 이용한 누락 수량 복원

- `app/receipt_columns.py`는 단가·수량·금액 머리글 위치가 확인될 때만 빈 수량을 복원한다. 머리글이 합쳐져 있으면 동일한 열 위치에서 계산이 맞는 본문 행 두 개 이상이 필요하다.
- 수량 열에 낮은 신뢰도 글자라도 있으면 덮어쓰지 않는다. 단가와 금액의 비율이 1~99의 정수인 경우만 후보로 채운다. 가격 두 개만 있다는 이유로 수량을 추측하지 않는다.
- `RECONSTRUCTED_PRICE_COLUMNS` 출처와 사용자 확인 안내를 붙인다. 직접 인식해 검산한 수량과 서버 로그에서도 구별한다.
- 기존 98장 개발용 스냅샷에서 수량 일치 115→125건, 이름·수량 동시 일치 61→66건. 정답 수량이 있는 행에서 잘못 채운 수량은 전후 모두 1건이다. 텍스트 기반 행 정렬과 초안 주석의 한계가 있어 독립 정확도로 해석하지 않는다.
- 새 5장 초안에서 수량 일치 6→9건, 이름·수량 동시 일치 3→5건. 이름 일치는 6건으로 그대로여서 상품명 분류 보완이 여전히 필요하다.
- 전체 테스트 287개 통과. 원본 사진과 DB는 변경하지 않았다.

## 평가 확장: 11장 주석 초안

개발용 152장 전체의 로컬 OCR 수집을 완료했다. 이전 캐시 80장과 이번 추가 72장이며 실패 0건이다. 해시 확인한 검수 목록도 152장 모두 캐시 완료 상태다. 원본 대조 주석 초안은 11장, 아직 주석이 없는 이미지는 141장이다. 수집 완료를 검수 또는 학습 완료로 해석하지 않는다.

IMG00051(이마트)와 IMG00287(홈플러스)의 원본을 대조했다. `맑은샘물2.0L*6`의 결제 수량 1과 묶음 안의 6개를 구별한다. 생략된 브랜드 과자·망고 음료·아몬드 상품은 원문을 보존하고 정확한 표준 품목 주석을 보류한다. 할인 행을 상품으로 추가하지 않는다.

- 식품 39행, 이름 정답이 있는 33행, 이름 일치 24건.
- 구매 수량 일치 20/39건, 이름·수량 동시 일치 14/33건.
- 이름 오류 3건, 미분류 6건, 이름 주석 보류 6건, 잘못 단정한 구매 수량 0건.

- 자동 행 정렬과 AI 작성 주석을 사용한 개발 진단이다. 사람이 검증한 독립 정확도나 학습 결과로 발표하지 않는다. 고정 평가용 30장은 계속 미사용이다.

`python -m scripts.build_new_receipt_review_queue`는 개발용 이미지의 OCR 캐시 해시를 검사하고 `output/new_receipts/review_queue.json`에 검수 순서를 만든다. 상단 OCR의 매장명 힌트로 마트·편의점 후보를 먼저 표시하지만, 이 힌트는 정답 라벨이 아니며 다른 이미지를 제외하지 않는다. 모든 항목은 `human_verified=false`, `training_eligible=false`를 유지한다. 전체 테스트 363개 통과.

## 세부 상품명 보존 회귀 검증

이하 수치는 11장 시점이며, 최신 확장 결과는 마지막의 13장 기록을 참조한다.

- 명시적인 그린/블랙올리브, 미고랭/미고렝누들 표기를 일반 올리브·면류로 축약하지 않는다. 오일·소스·비식품 접미사가 붙거나 품목 자체가 생략된 경우에는 이 규칙을 적용하지 않는다.
- 검증된 카탈로그 exact 일치는 유지한다. 그 외 부분 일치보다 명시적인 상품 중심어를 우선한다. 기존 모델 파일은 수정하거나 재학습하지 않았다.
- 동일한 신규 11장 개발 스냅샷에서 이름 일치 24→26/33, 이름 오류 3→1. 수량 일치 20/39, 이름·수량 동시 일치 14/33은 그대로다. 남은 이름 오류는 감자칩의 OCR 오독 `감자침사워크림`이다.
- 기존 개발용 98장에서는 이름 일치 137, 수량 일치 125, 동시 일치 71, 이름 오류 31로 변경 전과 동일하다. 보고서: `output/receipt_readiness/after-specific-heads.json`.
- 실제 응답 매핑 경로에서 세부 상품명과 검산된 구매 개수가 유지되는 테스트를 포함하여 전체 375개 통과. 이 검증은 저장된 OCR 스냅샷/로컬 코드 기준이며 실행 중 서버 재시작이나 새로운 이미지 처리 시간 측정은 포함하지 않는다.

## 원본 검수 확대: 13장 및 가공품 중심어

## 보조 상품명 복원 후보 실험

`app/receipt_name_recovery.py`는 기본 분류가 unknown이고 이름이 비어 있는 행만 대상으로 후보를 만든다. 양쪽의 검산된 구매 수량 및 가격 배열 일치, 같은 위치, 모든 상품 행을 포함한 일대일 대응을 요구한다. 이미 확정한 이름과 비식품 분류는 덮어쓰지 않는다. 보조 이름은 명시적인 식품 중심어/신선식품 접미사/달걀 규칙 출처여야 하고, 해당 이름이 포함된 OCR 상자의 점수가 0.95 이상이어야 한다. 숫자 상자의 높은 점수는 이름 근거로 사용하지 않는다. 0.95는 이 실험의 필터이지 보정된 정확도/확률이 아니다.

`python -m scripts.evaluate_name_recovery`로 신규 17장과 기존 98장, 총 115장 개발 캐시를 조사했다. 결과는 `output/receipt_readiness/name_recovery_proposals.json`. 후보는 IMG00594 피자 한 행뿐이며 기본 오독 원문과 보조 원문, 대응 행, 확인 필요 플래그를 함께 보존한다. 기존 98장에는 후보가 없었다. 이 표본에서 후보가 한 개라는 사실로 전체 오복원 위험이 없다고 결론내리지 않는다.

이 코드는 **후보만 생성**하고 운영 API에서 호출하지 않는다. 따라서 기본 정확도 수치가 개선된 것으로 집계하지 않았다. 구매 수량을 양쪽에서 모두 읽은 경우만 허용하여 회수율은 제한적이다. 식품명 복원 효과와 오류를 더 넓은 개발 주석에서 확인한 뒤 API 확인 후보로 연결할지 판단해야 한다.

## 세금 경계와 확인 목록 잡음 감소

### 보관 방식 불명확 시 날짜 미추정

프론트의 `receiptApi.ts`가 null 날짜를 빈 문자열로 변환하고 `review.tsx`가 등록 전 날짜 입력을 검증함을 읽기 전용으로 확인했다. 현재 OCR 업로드는 AI `/ocr`에 직접 요청하는 경로다. 등록 DB의 날짜 필수 제약은 변경하지 않았다.

AI의 ReceiptInventoryItem.consumeByDate를 nullable로 확장하고, unknown/지원하지 않는 보관 방식에는 날짜를 임의 생성하지 않는다. 제품 표시와 날짜·보관 위치 입력을 요구하는 안내를 반환한다. 알려진 보관 방식의 기존 추정 기한은 유지하되 여전히 제품 실제 소비기한이 아니라는 안내가 필요하다. 프론트/백엔드 파일은 미수정이다.

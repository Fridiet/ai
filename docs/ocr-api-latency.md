# 로컬 OCR API 시간 및 응답 안정성

실행: `python -m scripts.benchmark_receipt_api --repeats 3`

개발용 IMG00014, IMG00023, IMG00238을 `/api/ocr/receipt`에 순차 전송했다. 사진별 초기 요청 1회와 반복 3회, 총 12회다. DB 저장 API는 호출하지 않았다. 평가용 30장은 제외했으며 원본 SHA-256을 확인했다. 결과 원문은 저장하지 않고 응답 해시·항목 수·요청 시간만 기록한다.

## 이번 측정

- 총 12회 모두 HTTP 200, 실패 0회.
- 초기 요청 3회를 제외한 반복 9회의 p50 약 3.93초, p95 약 4.68초.
- 사진별 4회 응답 해시가 동일했다. 이는 출력 안정성이지 정확성 증거는 아니다.
- 첫 요청은 약 9.28초였다. 같은 서버 로그의 첫 OCR 단계에서 엔진 로딩 5.309초, 추론 3.627초, 후처리 0.291초가 확인됐다. 모든 요청의 제어된 콜드 스타트 실험은 아니며 OS 파일 캐시/모델 다운로드 시간은 측정하지 않았다.
- 이후 로그의 엔진 로딩은 0초이며 대부분의 시간은 이미지 추론에 소요됐다. 캐시된 분류 후처리는 대략 0.1초 수준이었다.

검출 장변 설정은 기존 0이고 보조 OCR은 사용하지 않았다. 첫 요청 5개 자동 채움/5개 확인, 두 번째 사진 4개/2개, 세 번째 사진 11개/1개였다. 자동 채움에도 이름·수량 오류가 남아 있으므로 이 개수를 정답 수로 해석하지 않는다.

## 한계와 재실행

같은 PC의 소량 순차 표본이므로 서비스 지연 보장이나 안정적인 운영 p95 추정치가 아니다. 동시 사용자, 대기열, 여러 해상도, 여러 촬영 상태는 별도로 측정해야 한다. p95는 정렬 표본의 선형 보간으로 계산하고 실패 요청은 별도 집계한다. 실패를 짧은 성공 시간으로 처리하지 않는다.

상세 로그: `output/receipt_readiness/api_benchmark.json` (재실행 시 교체), 서버 단계 로그: `output/ocr-api.stderr.log` (서버 재시작 시 교체될 수 있음). 이 실험 도중 서버를 재시작하거나 OCR 설정을 바꾸지 않는다.

코드 테스트 361개 통과. 이번 변경은 측정 도구와 테스트이며 운영 분류·검출 설정은 바꾸지 않았다.

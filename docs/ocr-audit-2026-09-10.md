# OCR 결과 보정 진단 및 수정 결과

## 2026-09-11 반영 결과

아래의 9월 10일 진단을 기준으로 로컬 수정과 동일 JPG 재검증을 완료했다.
원본 OCR은 188개, 최종 후보는 20개이다. 후보 수는 정확도를 뜻하지 않는다.

- 단가 × 구매 수량 = 합계가 맞는 행만 구매 수량을 곱한다. 불일치 시 추측하지 않는다.
- 고등어 3개, 애호박 2개, 양상추 2개. 우유 900ml×2=1800ml, 달걀 10입×2=20개 회귀 테스트 통과.
- 할인/포인트/계육 행사 안내행을 신규 상품에서 제외한다. 할인액을 구매 가격에 재배분하는 기능은 아니다.
- 닭볶음용·삼호어묵 동의어, 발사믹올리브의 드레싱 분류를 보완했다.
- 김 15매를 15장으로 표준화했다. 자두·청양고추·팽이버섯·주꾸미의 카테고리를 보완했다.
- `/ocr` 응답에 선택적 `rawText`, `reviewNotes` 필드를 추가하고 프론트 검토 카드에서 표시한다.
  기존 6개 필드는 유지된다. 원문 확인, 수량 검산 불가, 포장 용량 미확인, 날짜/보관 추정 안내를 제공한다.
- 프론트에서 UNKNOWN 보관 위치를 자동 냉장으로 변환하지 않고 등록 전 직접 선택을 요구한다.

남은 한계: 우유의 `2L`에서 L 누락, 닭고기의 `800g`→`8009`, 일부 브랜드/버섯 세분류 오류,
일부 식품 행 누락은 여전히 있다. 확실하지 않은 단위는 임의 복원하지 않는다.
소비기한은 처리일 기준의 고정 추정값이며 제품 표시 기한이나 안전성 검증 결과가 아니다.
영수증 다수에 대한 수작업 정답셋과 이미지 기준 정확도 평가는 추가로 필요하다.

## 2026-09-10 진단 기록 (수정 전)

사용자가 이전에 제공한 마트 영수증 JPG를 현재 `/ocr/raw` 서버에서 재실행하고,
동일 원본 결과로 상품행 분석 → 재고 후보 → 팀 API 형식 변환을 실행했다.
원본 OCR 188개, 최종 재고 후보 19개. **정확도 수치가 아니라 출력 개수**이다.
개인정보가 포함될 수 있는 상세 원문은 Git 제외 경로 `AI/output/ocr_audit.json`에만 보관한다.

## 확인한 문제

| 우선순위 | 재현 결과 | 수정 방향 |
|---|---|---|
| 1 | 실제 영수증의 할인행 `계육 2월1추 포항점 2,160`이 닭고기 1개로 두 번 포함됨 | 음수/할인행을 앞 상품과 연결하고 신규 상품 등록 대상에서 제외. OCR이 마이너스를 누락해도 문맥 확인 |
| 1 | 실제 고등어 수량 3, 애호박 수량 2, 양상추 수량 2가 모두 1개로 나옴 | 단가·구매 수량·합계 열을 분리. 단가×수량과 합계 검산 및 불확실성 표시 |
| 1 | `체리부로닭볶음용800g`이 점수 0.62로 탈락. 실제 닭고기는 빠지고 위 할인행만 닭고기로 반환됨 | 상품명 브랜드/규격 정리, 닭볶음용 같은 부위·용도 동의어 보완. 전체 임계값을 낮추는 방식은 피함 |
| 2 | `CJ_삼호어묵얇은사각` 0.67로 제외, 버섯류는 넓은 `버섯`으로 통합 | 원문과 표준명을 함께 유지하고 누락 후보를 검토 대상으로 반환 |
| 2 | `풀무원 발사믹올리브`가 생재료 `올리브`로 매칭됨 | 원본 상품 카탈로그에서 소스/드레싱 등 제품 유형 확인 후 원재료 부분일치보다 제품 분류 우선 |
| 2 | 자두·청양고추·팽이버섯·주꾸미 이름을 카테고리 함수에 직접 넣으면 `etc` | 확장된 식재료 사전과 카테고리/보관 규칙을 단일 기준으로 동기화 |
| 2 | 최종 팀 API에 후보의 수량 기본값·매칭 신뢰도·보관 추정 경고가 남지 않음 | 원문/추정 근거/확인 필요 필드를 협의해 프론트 검토 화면에서 표시 |

합성 행으로 수량 처리만 따로 확인한 결과:

- `우유 900ml 2,000 2 4,000` → 900ml (포장당 900ml를 두 개 구매했다면 1,800ml이어야 함).
- `달걀 10입 3,000 2 6,000` → 10개 (20개 누락).
- `두부 300g 2,000 3 6,000` → 300g (900g 누락).
- `당근 1,000 2 2,000` → 1개 (구매 수량 2 무시).

수정 전 `build_inventory_candidates`는 상품명에서 찾은 첫 규격만 수량으로 사용했다.
상품명 규격을 찾지 못하면 1개로 기본 설정하며 영수증의 구매 수량 열은 곱하지 않는다.
`15매`, `2L`에서 단위가 OCR에 누락되는 경우 등도 별도 검토가 필요하다.

## 확인된 정상 동작과 평가의 한계

- 실제 이미지의 고등어·고추·당근·파인애플·양상추는 현재 추출된다.
- 샴푸·컨디셔너는 이 이미지에서 재고 후보로 선택되지 않았다.
- 기존 2개 회귀 샘플은 상품행/식재료 선별/표준명 지표 100%였고 관련 테스트 17개 통과.
  하지만 이 샘플은 미리 작성한 OCR 텍스트이며 실제 이미지 인식 성능 검증이 아니다.
- 샘플 평가는 수량·단위·보관·소비기한의 정확도를 검사하지 않아 위 문제가 있어도 통과한다.
- 날짜는 처리일 + 카테고리별 고정 일수로 생성된다. 제품 표시 소비기한이나 안전성을 확인한 결과가 아니다.
  숫자 값을 늘리거나 확정 소비기한으로 표현하는 변경은 하지 않았다.

## 권장 구현 순서

1. 이 실제 영수증의 전체 상품/할인행 정답을 작성하고 구매 수량·단위 평가 항목을 추가.
2. 상품행/할인행 분리 및 열 기반 수량 추출. 금액 검산 실패 시 사용자 확인 필요 처리.
3. 식재료·가공품 분류 보완, 원문과 정규화 결과·근거를 함께 유지.
4. 프론트 검토 화면에 기본값/추정/낮은 신뢰도 안내 연결.

9월 10일 진단 당시에는 OCR 모델·사전·분류 규칙·API 응답 형식을 변경하지 않았다.
재현: AI 폴더에서 `python -m scripts.audit_ocr_output --image <영수증 JPG 경로>`.

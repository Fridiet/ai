# 작은 수량 숫자 감지 실험

2026-09-12. 개발용 원본 IMG00051.png와 IMG00238.png에서 각각 기본값, 감지 임계값 0.15/상자 임계값 0.4, 같은 임계값+최대 변 960을 실행했다. 이미지 SHA-256과 development 분할을 검사했다. 미사용 평가 이미지는 접근하지 않았다.

|---|---|---:|---:|---:|

각 설정 한 번씩 순차 실행했다. 엔진 생성은 별도 집계되지만 첫 추론의 워밍업 효과는 배제되지 않았다. HTTP·대기·후처리 시간을 포함하지 않으며 지연 시간 SLA나 일반적인 속도 향상으로 해석하지 않는다. 정답은 기존 보조 검수 개발 초안이다.

## 기존 보수적인 수량 보완 함수로 재평가

기본 이름을 유지하고 민감도+960 결과의 검증된 수량만 보완하면 두 이미지 합계에서 구매 수량 및 이름·수량 동시 정답이 각각 6/16 → 8/16으로 늘었다. 이름 정답 14/16, 기존 확정 수량 유지, 잘못 확정된 수량 0건을 확인했다. 원본 OCR 시간과 보조 OCR 시간 합은 각각 6.31초와 5.60초이며 실제 통합 HTTP 지연 시간은 아니다.

단독 보조 결과의 모든 수량이 채택된 것은 아니다. 현재 보완 함수는 직접 인식되어 검산된 수량만 허용하며 상품명·좌표·가격 일치도 요구한다. 민감도만 바꾼 결과를 보완했을 때는 개선이 없었다. 해상도를 바꿔 전체 결과를 교체하면 IMG00051의 이름 정답이 줄어드므로 이를 그대로 운영에 적용하지 않는다.

## 다음 검증과 적용 상태

스크립트 `scripts/experiment_receipt_detector_sensitivity.py`와 재실행 없는 `--replay` 경로를 추가했다. 결과 원문과 행별 평가는 `output/new_receipts/detector_sensitivity.json`에 기록했다. 실제 운영 설정·모델·서버는 변경하지 않았다. 더 많은 개발 영수증, 반복 지연 시간, 잘못된 수량 증가 여부를 확인한 뒤 적용 여부를 판단해야 한다.

## 개발용 21장 전체 재검증

동일한 세 설정으로 21장 원본을 각각 다시 인식했다(총 63회). 기존 2장 결과는 보존했다. 결과 `output/new_receipts/detector_sensitivity_all.json`에는 모든 OCR 상자·원문·행 평가 및 보완 평가가 포함된다.

| 방식 | 이름 정답 /74 | 수량 정답 /91 | 이름·수량 동시 /74 | OCR 시간 표본 p50 / p95 |
|---|---:|---:|---:|---|
| 기본 | 54 | 51 | 29 | 3.81 / 7.57초 |
| 민감도 조정 단독 | 47 | 45 | 26 | 3.61 / 7.08초 |
| 민감도+960 단독 | 48 | 51 | 30 | 1.77 / 2.39초 |
| 기본+민감도 수량 보완 | 54 | 52 | 30 | 7.33 / 14.51초 |
| 기본+민감도960 수량 보완 | 54 | 58 | 35 | 5.65 / 9.25초 |

보완 두 방식 모두 기본 이름과 이미 확정된 수량이 보존됐으며 잘못 확정된 구매 수량은 0건이었다. 민감도960 단독은 기존보다 이름 정답이 감소하고 미대응 출력도 1건 발생했다. 따라서 빠르다는 이유로 기본 엔진 설정을 대체하지 않는다.

수량 보완 시간은 각 단독 실행의 측정 시간을 이미지별로 더한 값이다. 조건부 호출이나 실제 HTTP 전체 지연 시간을 측정한 것이 아니다. 모든 이미지에서 보조 인식을 실행한 비용을 나타내며, 설정당 이미지별 1회만 실행해 반복 측정 분산과 워밍업 효과도 남는다. 테스트를 동시에 실행한 구간도 있어 엄밀한 성능 벤치마크로 해석하지 않는다.

기본+민감도960의 이름·수량 수정 필요율은 정답이 있는 74행 기준 45/74(60.8%) → 39/74(52.7%)다. 보관 위치·소비기한·총량은 이 비율에 포함하지 않으며 자동 등록 준비율로 바꾸어 부르지 않는다. AI 검수 초안이고 개발에 사용한 이미지이므로 독립 정확도도 아니다. 개선됐지만 목표인 대부분 자동 준비에는 아직 부족하다.

전체 회귀 테스트 549개 통과. 이번 작업은 실험 도구·검증 자료만 추가했고 실행 서버·프론트·백엔드·원격 저장소는 변경하지 않았다. 다음 단계는 기존 보조960 설정 대비 이득 비교, 조건부 호출과 지연 시간 검증, 다른 영수증에서의 오수량 회귀 점검이다.

## 조건부 실행 및 기존 보조 OCR와의 대조

`--replay --gated`는 기존 `needs_secondary_count_recovery` 조건으로 보조 인식 필요 여부를 평가한다. 식품명·가격이 있으나 구매 수량이 없는 상품이 있을 때만 실행한다. 21장 중 10장에 실행해 민감도960 보완의 이름 54/74, 수량 58/91, 동시 정답 35/74, 잘못 확정 수량 0건을 유지했다. 저장한 시간으로 산출한 합산 표본 p50/p95는 4.79/7.95초다. 이는 실시간 HTTP 측정이 아니다.

기존 민감도 기본값의 보조960 캐시가 있는 동일 19장만 대조했다. 두 편의점 이미지 IMG00254/IMG00298은 기존 캐시가 없어 모든 비교군에서 함께 제외했다. 기본 분석은 이번에 재실행한 동일 결과를 사용했다.

| 동일 19장 비교 | 이름 /71 | 수량 /86 | 이름·수량 /71 | 수량 오답 |
|---|---:|---:|---:|---:|
| 기본만 | 51 | 49 | 27 | 0 |
| 기존 보조960 조건부 | 51 | 56 | 34 | 0 |
| 민감도960 조건부 | 51 | 56 | 33 | 0 |

**결정: 새 민감도 설정은 운영에 채택하지 않는다.** 기본 대비 효과만으로 기존 보조 방식보다 개선됐다고 판단하면 안 된다. 기존 보조960이 동일 비교군의 이름·수량 동시 정답에서 1건 더 높았다. 새 보조960 실험의 효과를 신규 개발 성능 향상으로 주장하지 않는다. 기존 캐시는 이전 실행 결과라 실행 환경 차이 가능성이 있으며 시간 우열도 이 대조로 판단하지 않는다.

비교 도구 `scripts/compare_receipt_secondary_profiles.py`, 결과 `output/new_receipts/secondary_profile_comparison.json`. 이후 작업은 기존 보조960의 누락된 2장 검증, 조건부 실행 실제 HTTP 지연 시간과 오수량 회귀 확인이다. 아직 실행 중 서버는 변경하지 않았다.

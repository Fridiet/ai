# 실사용 OCR 목표와 경량 파이프라인

## 새 목표

개발 자료의 argmax 정확도 90% 대신 다음을 함께 검증합니다.

1. 실제 상품의 이름 반환 여부, 보류, 누락을 각각 집계한다.
2. 식품으로 반환한 비식품 수를 집계한다.
3. 결과 캐시가 없는 요청의 OCR 시간과 후처리 시간을 분리한다.
4. 상품명은 읽었으나 수량을 못 읽은 행을 삭제하지 않는다.
5. 특정 영수증 수정 결과를 전체 정확도나 재학습 성과로 주장하지 않는다.

## 현재 정책

비식품 명시어 → 가공상품 사전 → 신선식품 끝 일치/정확 식재료 사전 → 명시적 식품명 규칙 → 경량 학습 분류기 → 검토 대상.

`FastOCRNormalizer`는 봉인된 v7 문자/E5 분류기를 사용합니다. 고정 체크포인트 및 코드 해시를 검사하고
로컬 파일만 읽습니다. Qwen은 로딩/호출하지 않습니다. 온라인 고비용 호출 한도는 **0회**입니다.
무거운 모델의 재도입은 처리 시간과 보류 해소 효과가 검증된 이후 별도 결정해야 합니다.
학습 모델의 불확실한 결과를 무조건 채택하도록 임계값을 낮추지는 않았습니다.
`OCR_CLASSIFIER_ENABLED=false`로 재시작하면 기존 사전 경로로 돌아갑니다.

`(990)청양고추` 같은 선두 괄호 숫자를 상품 가격으로 잘못 자르지 않습니다.
상품 표 끝인 총 품목 수량/결제 대상 금액 이후 세금 행은 상품으로 보지 않습니다.
미분류된 가격 있는 상품은 구매 수량이 없어도 검토 목록에 남깁니다.
`reviewCandidates[].purchaseCount`는 이때 `null`입니다. 기존 프론트는 `?? 1` 처리를 사용합니다.

가공상품 사전에 비피더스명장·카스후레쉬를 추가했습니다. 이는 외부 데이터 학습이 아닌 명시적 상품 매핑입니다.
유정란→달걀, 모둠쌈→쌈채소, 등심→등심을 처리합니다. 등심만으로 축종을 소고기로 단정하지 않습니다.
청양고추는 기존 표준 사전에 따라 고추로 매핑됩니다. 원문은 유지됩니다.
15개입 포장은 달걀 15개로 파싱합니다. 맥주의 `355m]*6` 같은 OCR 오류는 용량을 지어내지 않고 검토 안내를 남깁니다.

## 첨부 원본 영수증 검증

파일: 스크린샷 2026-07-17 212620.png (총 상품 15개).
수정에 사용한 개발 회귀 자료이며 독립 테스트가 아닙니다.

| 항목 | 이전 | 수정 후 |
|---|---:|---:|
| 식품·음료 이름 반환 | 5/11 | 11/11 |
| 비식품 검토 목록 혼입 | 4 | 0 |
| 실제 식품 누락 | 2 | 0 |
| 미분류 검토 목록 전체 | 8 | 0 |
| 상품 후처리 | 약 25.8초 | 0.154초 |

최종 서버 재시작 후 첫 원본 이미지 요청: HTTP 200, 총 **8.422초**.
OCR 최초 로딩/인식 8.223초와 후처리 0.154초를 기록했습니다.
이전 기록의 약 28.3초와 실행 환경/초기화 상태가 완전히 통제된 벤치마크는 아니며,
후처리의 Qwen 제거 효과를 확인한 것입니다. 결과 캐시는 재시작으로 비워졌습니다.

반환 이름: 요구르트, 양파, 대파, 당근, 쌈채소, 콩나물, 고추, 등심, 달걀, 라면, 맥주.
스푼·국자·면봉·불스원샷은 제외했습니다. 이 원본은 모든 행이 사전/규칙 경로로 처리됐으며
**11/11은 학습 모델 정확도가 아닙니다.** 수량/포장·축종·소비기한·보관 방식은 여전히 확인이 필요합니다.

검증 스크립트: `python -m scripts.verify_original_receipt_fast`
결과: `output/original_receipt_fast_http.json` (Git 제외).
관련 회귀 테스트 **109개 통과**. 프론트/백엔드/DB 수정, 커밋, push는 수행하지 않았습니다.

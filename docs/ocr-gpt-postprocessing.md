# 영수증 상품명 GPT 보정

## 현재 상태

AI 폴더 내부에만 구현했습니다. 코드/예시 기본값은 `OCR_LLM_ENABLED=false`이지만,
사용자의 운영 적용 요청에 따라 현재 로컬 AI `.env`는 `OCR_LLM_ENABLED=true`로 설정하고 재시작했습니다.
**독립 영수증 30장 평가가 완료된 정식 정확도 인증이 아니라, 서버 검증을 동반한 제한적 운영 적용입니다.**
`/ocr`, `/api/ocr/receipt`에서만 기존 OCR·수량 복구 다음에 실행됩니다. 원문 OCR,
재고 후보 조회/직접 저장 API, 용기 잔량 기능은 적용 대상이 아닙니다.
기존 `items`, `reviewCandidates` 구조는 유지합니다. 내부 상품 처리에는 GPT 보정 확인 안내가 추가됩니다.
이 안내는 내부 처리 단계에 남습니다. 2026-10-04 사용자 요청으로 최종 운영 응답의 `reviewNotes`는
빈 배열로 정리하고 기존 프론트 상단의 공통 추정 안내만 표시합니다. 모델 적용 여부는 운영 로그에서 확인합니다.
내부 후보 매칭 유형에는 `llm_validated`가 추가되며 score는 규칙 통과 표시이지 통계적 정확도/확률이 아닙니다.

## 설정

AI `.env`에서만 관리합니다. 프론트에 API 키를 넣지 마세요.

```dotenv
OPENAI_API_KEY=기존_서버_키
OCR_LLM_ENABLED=true
OPENAI_OCR_MODEL=gpt-5.4-mini
OCR_LLM_TIMEOUT_SECONDS=8
```

설정 후 AI 서버 재시작을 권장합니다. 기존 uvicorn 실행에 `--env-file .env`를 사용합니다.
새 환경에서는 API 비용과 검수 범위를 확인한 뒤 true로 설정합니다. true로 바꿔도 키가 없으면 기존 결과를 반환합니다.
대기 제한은 최대로 8초이며 더 큰 설정값은 8초로 제한됩니다. 선택·요청 대기·검증도 제한에 포함됩니다.
시간 초과된 스레드 작업은 끝날 수 있으나 원본 분석/DB를 변경하지 않습니다.
동시 요청 2개, 영수증당 1회 호출/20행/행당 후보 5개, 자동 재시도 없음입니다.

## 전송/반영 규칙

- 상품명·행 ID·사전 후보만 텍스트로 전송합니다. 원문 전체, 가격, 구매 개수, 이미지, 사용자 ID는 보내지 않습니다.
- 이메일·전화·주소·카드 등 개인정보가 의심되는 행, 안내/할인/합계/비식품/프롬프트 지시 행은 제외합니다.
- OCR이 별도 바코드 셀로 표시했고 EAN/UPC 체크섬도 유효한 제품 바코드는 원문의 개인정보
  검사 문맥에서만 제외합니다. 원본/수량은 수정하지 않고 바코드도 GPT에 보내지 않습니다.
  식별되지 않은 긴 숫자, 잘못된 체크섬, 전화/카드 등 개인정보 라벨은 계속 차단합니다.
- 개인정보 필터는 보수적인 패턴 기반이며 완전한 익명화 보장은 아닙니다. 운영 로그/전송 표본을 별도로 점검하세요.
- 상품 행의 전체 정체성을 GPT가 검토합니다. exact/alias/contains/fuzzy/ML/미분류 모두 대상이며,
  기존 확정 매칭을 같은 이름으로 확인만 한 경우 기존 점수/매칭을 보존합니다.
- 가격/구매 개수 근거가 있는 행 최대 20개를 검토합니다. 가공식품 충돌·미분류·부분 매칭을
  이미 확정된 행보다 우선해 뒤쪽 상품이 예산 밖으로 밀리는 문제를 방지합니다.
- 후보 최대 5개는 힌트입니다. GPT는 후보 밖 표준명도 제안할 수 있지만 사전의 정확한 이름/유일한 앨리아스와
  실제 원문 근거를 모두 서버에서 확인해야 합니다. 사전에 없는 이름은 자동 생성하지 않습니다.
- 상품 종류 충돌 및 가공식품의 재료명 오분류를 거절합니다. 브랜드 제품군 근거로
  짜파게/짜파게티·오징어짬뽕을 라면으로 검증하며 올리브/오징어 원재료로 분류하지 않습니다.
- GPT가 기존 가공식품 오분류를 확정하지 못한 경우, 성공한 검토에서 확인된 제품군 충돌은
  미분류로 전환해 잘못된 원재료의 자동 등록을 막습니다. 실패/시간 초과 시에는 기존 분석을 보존합니다.
- 그릭 무가 등 텍스트만으로 부족한 축약은 확정하지 않습니다. OCR에서 누락된 글자 복구/이미지 재판독 기능이 아닙니다.
- 짧은 재료명은 명시적 토큰 또는 한정된 수식어 제거로만 인정합니다. 오이스터의 오이를 부분 문자열로 인정하지 않습니다.
- 후보 설명은 서버가 작성합니다. 모델의 자유 설명을 그대로 사용자에게 전달하지 않습니다.
- 기존 매칭을 근거 없이 덮어쓰지 않습니다. 보정 전 원문의 수량 파싱을 고정하고 가격·구매 개수 근거를 그대로 유지합니다.
- 상품명 단계에서는 기한/보관 방식/수량을 생성하지 않습니다. 뒤의 날짜 누락 보완 기능은 별도이며
  `docs/ocr-general-storage-dates.md`를 참고하세요. DB 쓰기 없음입니다.
- 타임아웃/429/키 오류/거절/중복 ID/잘못된 JSON은 원래 분석 결과로 복귀합니다.
- 응답에 요청하지 않은 행이나 누락된 행이 있으면 불완전 검토로 처리해 원래 결과로 복귀합니다.
- 요청은 `store=false`, TLS 검증 활성입니다. 이는 API 제공자의 모든 데이터 보관 정책을 없앤다는 뜻이 아닙니다.
- 로그는 시간/반영 건수/실패 유형/토큰 수만 기록합니다. 응답 원문·상품명·키는 기록하지 않습니다.

## 평가 준비와 실행

PowerShell에서 AI 폴더 기준:

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
.\.venv\Scripts\python.exe -m scripts.evaluate_receipt_llm --prepare --manifest output/receipt_llm/current_manifest.json
.\.venv\Scripts\python.exe -m scripts.evaluate_receipt_llm --manifest output/receipt_llm/current_manifest.json
```

준비된 manifest를 덮어쓰지 않습니다. 현재 30장(개발 10/평가 20)은 기존 로컬 OCR 캐시를
현재 상품 파이프라인으로 재분석해 선정했습니다. 알려진 중복 거래 그룹/이미지 해시는 분리했습니다.
누락된 중복 거래가 없는지는 사람이 추가 확인해야 합니다. 이미 개발에 열람한 영수증이므로 독립 테스트가 아닙니다.
캐시 사용 평가에는 실시간 OCR 재인식/보조 수량 복구 시간은 포함되지 않습니다.

`reference_suggestions`는 과거 AI 주석이고 정답이 아닙니다. 사진과 OCR 행을 비교해 모든
`expected_rows.canonical_name`을 현재 사전 이름으로 확인하세요. null은 비식품/확정 불가/제외입니다.
각 행 `verified=true`, 영수증 `human_verified=true`, `verified_by`에 검수 식별자를 기록해야 합니다.
중요 오분류 행은 `critical_row_ids`에 표시합니다. 이 표시는 실제 검수 후에만 설정하세요.

확인된 정답이 30장 전부 있어야 유료 평가가 열립니다:

```powershell
.\.venv\Scripts\python.exe -m scripts.evaluate_receipt_llm --manifest output/receipt_llm/current_manifest.json --live
```

보고서는 동일 폴더 `report.json`입니다. 대상 행 정확도 전후, 자동 반영 정확도(정답 반영/전체 반영),
미분류 해소율, 회귀 건수, 추가 지연 P95, 토큰 수를 개발/평가로 나눠 보고합니다.
비용 추정이 필요하면 최신 계정 가격에 맞춘 `OCR_EVAL_INPUT_USD_PER_M`, `OCR_EVAL_OUTPUT_USD_PER_M`를 설정합니다.
취소/완료되지 않은 요청의 토큰은 집계되지 않을 수 있어 실제 청구와 다를 수 있습니다.

통과 기준: 평가 자동 반영 정확도 ≥95%, 대상 행 정답 수 증가, 모든 회귀 0건,
추가 대기 P95 ≤8초(측정 오차 허용 0.1초), 오류 복귀/수량 보존 테스트 통과.
반영 0건은 통과가 아닙니다. 표본 수와 함께 해석하고 전체 영수증 정확도라고 표현하지 않습니다.
이 도구는 `.env`를 수정하지 않습니다. 위 기준은 독립 검수 데이터에 대한 정식 정확도 평가 기준입니다.
현재 사용자가 요청한 제한적 운영 활성화와 구분하며, 아직 기준 통과를 주장하지 않습니다.

## 이번 검증 결과와 남은 조건

상품명·장애·개인정보·바코드 구분·주입·후보 밖 이름·수량 보존·API 범위 테스트를 포함해 전체 테스트 905개가 통과했습니다.
실제 `gpt-5.4-mini` 텍스트 회귀 검사 32건에서 사전 기준 28/32 → 검토 후 32/32,
최근 검사에서 반영 5건 중 5건 정답, 회귀 0건, 16행씩 2회 호출 각 약 4.09초/3.18초를 확인했습니다.
LLM 출력은 실행별로 달라질 수 있으며 이 작은 표본으로 일반 성능을 보장하지 않습니다.
상품 원문/가격/구매 개수 및 등록 수량/단위 보존을 검사했습니다.
이는 **준비된 텍스트 회귀 사례의 결과**로 전체 영수증 정확도 또는 독립 검증 성능이 아닙니다.
`output/receipt_llm/live_regression.json`과 다음 명령으로 재현할 수 있습니다(유료 호출):

```powershell
.\.venv\Scripts\python.exe -m scripts.verify_receipt_llm_live
.\.venv\Scripts\python.exe -m scripts.verify_receipt_ocr_service "영수증_이미지_절대경로"
```

두 번째 명령은 실제 운영 `/api/ocr/receipt`에 사진을 업로드하며 DB 저장하지 않습니다.
실제 운영 사진 확인 결과:

- `IMG00152.png` → `/ocr` HTTP 200, 달걀·라면·라면 3상품, 미분류 0.
  농심 올리브짜파게티 행은 GPT 상품명 보정 안내와 함께 라면으로 반환됨.
  보고서: `output/receipt_llm/operational_chapagetti.json`.
- `스크린샷 2026-07-17 212620.png` → `/api/ocr/receipt` HTTP 200,
  양파·대파·당근·청양고추·달걀·라면 등을 포함한 11식품, 미분류 0.
  보고서: `output/receipt_llm/operational_receipt.json`.
- 최종 실행 사진의 전체 요청 시간은 각각 약 17.60초(첫 OCR 엔진 로드 포함)/12.08초.
  전체 시간은 OCR·보조 수량 복구·상품명 GPT·별도 기한 제안·통신 시간을 모두 포함하며,
  상품명 보정 단계 자체의 8초 제한과 구분해야 함.

운영 시작 로그의 `OCR llm configuration enabled=True key_configured=True`와 요청 로그의
`selected`/`accepted`/`status`/`tokens`를 함께 확인하면 설정만 켜고 적용되지 않은 경우를 구분할 수 있습니다.
기존 156장 주석의 사람 검증 상태는 false이고, 준비된 30장도 검증 완료 0장입니다.
평가 도구가 자동 생성 주석을 정답으로 받아들이지 않고 차단하는 것을 확인했습니다.
이 검수는 여전히 남아 있으며 제한적 운영 활성화가 이를 대신하지 않습니다.
평가 준비 중 기존 로컬 OCR 분류 모델의 코드 봉인 해시가 일치하지 않아 사전 파이프라인으로 폴백했습니다.
이번 작업은 봉인 대상 `app/ml` 파일/체크포인트를 수정하지 않았고 해시 검증을 우회하지 않았습니다.
실제 사용 모델과 같은 조건으로 평가하려면 이 기존 모델 검증 문제를 먼저 별도 해결해야 합니다.

## 복구

`OCR_LLM_ENABLED=false`로 설정하고 AI 서버를 재시작하면 기존 OCR 경로로 복귀합니다.
DB 마이그레이션/재고 데이터 변환은 없으므로 DB 복구 작업이 필요하지 않습니다.
이번 작업으로 프론트/백엔드/루트 파일은 변경하지 않았습니다. 이전 작업의 변경 사항은 그대로 보존했습니다.

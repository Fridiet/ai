# 수량 셀 재인식 API 연결

2026-09-12: `/ocr`, `/api/ocr/receipt`의 보조 수량 복구 뒤에 선택적 숫자 재인식을 연결했다. `OCR_SECONDARY_COUNTS_ENABLED=true` 및 `OCR_NUMERIC_CELLS_ENABLED=true`가 필요하며 기본값은 꺼짐이다. 현재 실행 중인 8000 서버는 변경하지 않았다.

- 기존 수량이 없는 이름 매칭 후보만 최대 4행, 행당 단가/수량/금액 3개 영역을 처리한다.
- 별도의 전체 이미지 검출은 추가하지 않는다. 960 보조 검출 결과의 열 위치를 사용한다.
- 모델은 지연 로드 후 캐시하고 기존 OCR 추론 잠금을 공유한다.
- 숫자 신뢰도, 곱셈 검산, 원문 충돌, 중복 행 검증은 기존 숫자 병합 함수를 사용한다.
- 실패 시 보조 OCR까지 복구한 결과를 보존한다. 검산 수량은 확인 안내를 유지한다.

## 확인 결과와 한계

개발용 IMG00238.png 원본 이미지를 실제 숫자 인식기에 전달했다. 주 OCR/보조 OCR은 저장된 결과를 사용했다. 감자칩과 드레싱 구매 수량 각각 1개가 NUMERIC_CELLS_VERIFIED로 복구됐다. 첫 실행은 모듈 import/모델 로드를 포함하여 7.014초였으며, 전체 HTTP 요청 시간이나 웜 상태 지연 시간이 아니다.

전체 회귀 테스트 659개 통과. 추가 4개는 후보 수 제한, 수량 있는 행 제외, 헤더 없을 때 추론 생략, 정상 병합 및 결과 개수 불일치를 검사한다.

실제 HTTP 통합 검증, 웜 상태 지연 측정, 여러 영수증에서 제한된 후보 선택의 복구율 검증이 남아 있다. 독립 평가 세트는 열지 않았고 이 결과는 일반화 정확도가 아니다. 후보 개수 제한은 실행 시간의 강제 상한을 보장하지 않는다.

## HTTP 검증 후속

임시 8011 서버에서 숫자 셀 옵션을 켜고 개발용 IMG00238, IMG00240, IMG00254를 각 3회 요청했다. 9회 모두 200이며 각 이미지의 응답 해시가 일치했다. 반복 6회 중앙값 6.026초, 표본 p95 7.996초. 첫 요청 14.530초에는 주 OCR 모델 로드 5.459초와 숫자 모델 로드 0.626초가 포함됐다. 숫자 재인식 추론 자체는 9개 영역 약 0.25초, 3개 영역 약 0.06초였다. 이는 이 PC의 소규모 직렬 측정이며 운영 SLA가 아니다.

보고서: `output/receipt_readiness/api_numeric_cells_20260912.json`.

응답 의미 검증: IMG00238의 감자칩은 110g, 드레싱은 1개로 반환되고 두 항목 모두 숫자 영역 검산 안내가 포함됨을 HTTP로 확인했다. 최초 검증 명령은 구매 개수와 반환 재고량을 혼동하여 둘 다 1개라고 기대해 실패했다. 실제 명세에 맞춰 감자칩 110g × 구매 1개 = 재고 110g으로 기대값을 수정하고 재요청해 통과했다. 상품 분량 정보를 버리지 않는다.

숫자 인식 실패 시 앞선 보조 수량 복구를 유지하는 API 단위 테스트를 추가했다. 이번 HTTP 서버는 이후 추가한 로그 필드 변경을 포함하지 않으며 추론 로직은 동일하다. 8000 운영 서버는 여전히 변경하지 않았다. 다음에는 개발 세트 전반의 제한된 후보 선택 및 실제 사용자 수정 필요율을 확인해야 한다.

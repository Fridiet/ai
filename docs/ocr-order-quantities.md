# 주문 내역 OCR 내용량 계산 개선

수정 범위: AI 내부. 프론트·백엔드·DB 데이터는 변경하지 않았다.

## 적용 방식

- `/ocr`, `/api/ocr/receipt`에서 반복되는 상품 카드와 가격/구매 개수 행이 있을 때 주문 내역 전용 분리를 적용한다.
- 상품명의 여러 줄을 연결하고, 포장 내용량과 묶음 수, 실제 주문 개수를 구분한다.
- `1L,2개`는 2,000mL, `420g,2개입,1세트`는 840g, `70g,1개`를 2개 주문한 경우 140g으로 반환한다.
- `500g 2봉`처럼 명시된 포장 내용량은 일반 영수증 수량 파서에서도 처리한다. 단가·구매 개수·금액 열의 숫자는 포장 수로 사용하지 않는다.
- 용량의 g/mL 글자가 불명확하면 해당 글자 영역을 확대해 추가 인식한다. `3009`를 문자열 규칙만으로 `300g`으로 바꾸지 않는다. 숫자와 개수 일치, 인식 신뢰도를 검증한다.
- GPT 상품명 보정은 검증된 주문 내용량을 덮어쓰지 않는다.
- kg→g, L→mL는 십진수로 정확히 환산한다. 추천의 기존 수량 비교 함수도 같은 단위를 인식한다.

## 남겨 둔 확인 대상

- 개수만 적힌 오이·양배추·애호박: 개수 그대로 반환한다. 평균 무게를 만들어내지 않는다.
- `1.2kg 내외` 바나나: 정확한 잔량으로 확정하지 않고 포장 개수 및 내용량 확인 안내를 반환한다.
- 소스 포함 연두부 세트의 804g: 소스 무게까지 연두부 재고로 계산하지 않는다.
- 모듬 다짐육과 동물 종류가 쓰이지 않은 사태는 임의로 소고기/돼지고기로 확정하지 않는다.

현재 수량 비교에서 2개 재고와 200g 레시피는 `UNKNOWN`(확인 필요)이며, 임의 무게 환산이나 확정 부족으로 판단하지 않는다. 프론트에서 이를 부족처럼 묶어서 표시하는지는 별도 프론트 점검 대상이다.

## 실제 검증

사용자가 제공한 주문 이미지 9장, 직접 확인한 상품 43개를 대상으로 기존/개선 API 결과를 저장했다.

- 기존 등록 후보 26개 → 개선 등록 후보 41개, 미분류 2개(모듬 다짐육·사태).
- 개선 결과 예: 양송이버섯 300g, 우유 2,000mL, 두부 600g, 식빵 840g, 샐러드 140g, 그릭요거트 720g, 대파 1,500g, 깻잎 90g.
- 근사치 바나나 2행과 소스 포함 연두부 1행은 내용량 확인이 필요하다. 이들을 정확한 g 재고로 집계하지 않았다.
- 평가 파일: `output/home_orders/baseline.summary.json`, `final.summary.json`, 이미지별 원문/응답 JSON.
- 해당 9장의 개선 결과이며 다른 영수증 전체에 대한 정확도 주장으로 일반화하지 않는다.

이미 DB에 저장된 `1개` 재고는 이 변경으로 자동 환산되지 않는다. 원본 포장량 확인 후 수정하거나, 재고 중복이 없도록 기존 배치를 확인하고 개선된 OCR 결과를 새로 등록해야 한다.

## 테스트 및 복구

`python -m pytest -q`로 단위/회귀 테스트를 실행한다. `tests/test_online_order.py`는 묶음 수, 구매 수, 여러 줄, GPT 수량 보존, 잘못 읽은 단위, 추천 수량 비교를 검증한다.

기존 동작으로 복귀하려면 `main.py`의 주문 카드 분기만 원래 영수증 처리로 되돌리고 AI 서버를 재시작한다. 이번 작업에서 DB를 변경하지 않았으므로 DB 복구는 필요 없다. 기존 `inventory_mapper.py` 수정 중 이번에 추가한 명시적 묶음 파싱과 주문 내용량 우선 적용만 제거하면 된다. 다른 미커밋 변경은 보존한다.

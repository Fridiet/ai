# OCR 시작 지연 및 동시 요청 개선

## 변경

- `OCR_STARTUP_WARMUP=true`: 서비스가 요청을 받기 전에 기존 OCR 모델과 활성화된
  숫자 인식 모델을 로딩하고 작은 빈 이미지로 실행한다. 별도 GPT 호출이나 DB 쓰기 없음.
  시작 준비 시간은 남지만 첫 사용자의 요청에 붙지 않는다. 준비 실패 시 시작 실패로 처리한다.
- `OCR_CPU_THREADS=2`: 2 vCPU 서버에서 과도한 스레드 경쟁을 피하도록 명시한다.
  모델·해상도·후처리 규칙은 변경하지 않는다.
- Python 3.10의 `asyncio.TimeoutError`를 명시적으로 처리한다.
  이전 `except TimeoutError`는 실제 시간 초과를 잡지 못해 ASGI 500을 발생시켰다.
  업로드 시간 초과에도 동일하게 적용한다.
- 동시 처리 2개, 추가 대기 최대 4개, 슬롯 대기 최대 30초.
  초과는 제어된 429이며 무제한 요청 적재나 추가 모델 인스턴스를 만들지 않는다.
  취소·시간 초과·업로드 실패 후 슬롯과 대기 용량을 반환한다.
- 앞서 해제한 분당·일일 요청 횟수 제한은 계속 0(해제)이다.
  인증·업로드 크기 제한은 유지한다.

## 검증

- 전체 로컬 테스트 1,054개 통과.
- 게이트웨이·시작 준비·OCR 옵션 관련 26개 테스트 통과.
- 실제 AWS의 주문내역 이미지 1장으로 CPU 10/2 스레드 비교:
  인식 텍스트 해시 및 17개 박스 수 동일. 반복 인식 4.730/4.627초로 차이가 작으므로
  지속 처리 속도가 크게 향상됐다고 주장하지 않는다. 단일 표본 결과이다.
- 배포 후 시작 준비 11.076초. 첫 실제 요청: 200, 12.786초, 등록 후보 5개,
  미분류 0개. 엔진 로딩과 숫자 모델 로딩은 요청 중 각각 0초.
- 실제 영수증 동시 2건: 모두 200, 16.016/16.199초.
  뒤에 대기시킨 잘못된 이미지 요청은 15.812초 후 정상적인 검증 오류 400.
  동시 요청에서 ASGI 500이 발생하지 않음을 확인했다.
- 외부 HTTPS health 200. 영수증 3건의 GPT 보정은 실제 실행했으며 DB 저장 없음.
- 이전 28.854초 로그의 이미지는 다른 이미지이므로 전후 개선율로 계산하지 않는다.
  이미지와 OpenAI 응답에 따라 실제 시간은 달라진다. 대기열 포화 시
  백엔드가 upstream 429를 502로 표시하는 기존 동작은 별도이며 변경하지 않았다.

## 적용 및 복구

AWS에 `app/main.py`, `app/ocr.py`, `app/public_gateway.py`, `app/public_server.py`와
위 환경 설정만 반영했다. 배포 도구는 기존 파일의 예상 해시를 확인하고
예상 밖 서버 변경이 있으면 중단한다. 시작 health 실패 시 자동 복구한다.

수동 복구 백업(root 전용):
`/var/backups/fridiet/ocr-runtime-20261027-141825/`

백업의 `app/` 파일들을 `/opt/fridiet-ai/app/`의 대응 파일로 복원하고,
`fridiet-ai.env`를 `/etc/fridiet-ai.env`로 복원한 뒤 권한 600을 유지하여
`sudo systemctl restart fridiet-ai`를 실행한다. 환경 파일의 비밀 키는 출력·공유하지 않는다.
이 백업에는 요청 횟수 제한 해제 상태가 보존되어 있다.

커밋·푸시 없음. 프론트·백엔드·DB 스키마 변경 없음.

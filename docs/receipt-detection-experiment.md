# 영수증 검출 해상도 비교 (개발용)

## 원인과 실험

IMG00238 원본에는 단가·수량·금액이 있지만 기존 raw OCR에는 일부 숫자 상자 자체가 없었다. 후처리만으로 복원할 수 없는 누락이다. 설치된 PaddleX OCR 설정은 검출 장변 최대 4000, 최소 변 64이며 원본 크기를 대부분 유지한다. 검출 크기와 점수 임계값을 별도로 비교했다. 인식기는 기존 한국어 PP-OCRv5 모바일 모델을 그대로 사용했다.

실행:

```powershell
.\.venv\Scripts\python.exe -m scripts.experiment_receipt_detection
.\.venv\Scripts\python.exe -m scripts.experiment_receipt_detection --profiles max1600 max960
.\.venv\Scripts\python.exe -m scripts.experiment_receipt_detection --profiles default max960 --all-annotated
```

`output/new_receipts/detector_experiment/`에 실제 OCR 상자·텍스트, 설정, 시간, 정렬 결과를 저장한다. 제공 이미지의 SHA-256과 development 분할을 검사한다. 평가용 30장은 사용하지 않으며 운영 API 설정을 변경하지 않는다.

## 결과

검출 임계값을 0.3/0.6에서 0.2/0.4로 낮춘 것은 세 마트 사진에서 이득이 없었다. IMG00014 수량 일치는 7→5로 감소했다. 채택하지 않는다.

장변 960 검출 비교: 원본 대조 초안 7장, 식품 25행(이름 정답 24행).

| 항목 | 기본 | 장변 960 |
|---|---:|---:|
| 이름 일치 | 18 | 17 |
| 수량 일치 | 14 | 21 |
| 이름·수량 동시 일치 | 12 | 16 |
| 이름 오류 | 2 | 1 |
| 틀린 수량 자동 채움 | 0 | 0 |

IMG00238 수량 일치는 5/12→11/12로 개선됐다. 그러나 IMG00023의 `캐슈너트`가 `캐습너트`로 바뀌면서 이름 자동 채움이 한 건 줄었다. 기존 사워크림 오분류도 장변 960에서는 확인 대상으로 바뀌었다. 비식품 정답이 있는 행의 식품 승격은 두 설정 모두 0건이었다.

세 주요 마트 사진의 이번 OCR 추론 시간은 기본 약 4.6~5.5초, 장변 960 약 2.2~3.4초였다. 모델 생성·전체 HTTP·분류 시간을 포함하지 않으며 순차 단회 측정이다. 다른 작업과 CPU를 공유한 구간도 있어 p95 또는 확정 속도 개선율로 주장하지 않는다.

## 결정과 남은 작업

- 장변 960은 수량 누락과 지연에 유망하지만 아직 운영 기본값으로 바꾸지 않았다.
- 다음 비교는 더 많은 개발 영수증 및 기존 시연 사진에서 이름/수량 퇴행 확인이다.
- 이름 정체성이 불명확한 행만 원본 해상도로 재인식하는 선택적 보완을 검토하되, 전체 이미지를 매번 두 번 OCR하는 방식의 지연을 기본 비용으로 추가하지 않는다.
- 독립 평가와 전체 자동 등록 준비율은 여전히 미달·미검증 상태다.

## 기존 98장 확대 비교

`python -m scripts.compare_detection_history`로 기존 개발용 마트/편의점 98장을 모두 비교했다. baseline은 기존 raw 캐시를 현재 후처리로 다시 분석했고, max960은 원본 SHA-256 확인 후 다시 OCR했다. 따라서 baseline의 과거 처리 시간과 현재 추론 시간을 직접 비교하지 않는다. 새 결과는 해시별로 저장하여 중단 후 재개할 수 있다. `output/receipt_readiness/detection_history/comparison.json`에 98/98 완료를 기록했다.

| 항목 | 기존 raw + 현재 후처리 | max960 + 같은 후처리 |
|---|---:|---:|
| 이름 일치 (정답 있는 303행) | 133 | 137 |
| 수량 일치 (311행) | 125 | 170 |
| 이름·수량 동시 일치 | 70 | 91 |
| 이름 오류 | 33 | 35 |
| 틀린 수량 채움 | 1 | 1 |

수량과 누락은 개선되지만 잘못 채우는 이름도 늘었다. 예를 들어 `안심신선왕란30구`의 안심을 육류 재료로 취급하는 부분 일치가 드러났다. 모든 사진에 무조건 축소 설정을 적용하는 것으로 완료했다고 판단하지 않는다. 해당 분류 충돌 및 사진별 퇴행을 먼저 검증해야 한다.

`OCR_DETECTION_MAX_SIDE` 옵션을 추가했다. 0은 기존 설정 유지, 256~4000은 검출 장변 제한이며 960은 이번 실험값이다. 원본 인식 입력을 직접 축소하지 않고 검출기에만 옵션을 전달한다. 잘못된 값은 모델 실행 전에 거부한다. 소스 기본값과 `.env.example`은 0이고 실행 중인 API 설정은 바꾸지 않았다. 회귀 테스트 311개 통과.

## 달걀 충돌 수정 후 재검증

`왕란·유정란·무정란·계란·달걀`로 끝나는 상품명에 숫자+구/입/개/판 포장 표기를 허용하고, 해당 정체성을 안심 같은 부분 일치보다 먼저 판정한다. 구운/훈제/반숙/소금 등 조리 문맥은 이 생달걀 규칙에서 제외한다. 돼지안심은 그대로 유지한다.

수정 후 같은 98장 캐시 재분석: max960 이름 일치 137→139건, 이름 오류 35→33건. 수량 일치 170건과 이름·수량 동시 일치 91건은 동일하다. 기존 해상도 결과는 이름 133건/수량 125건/동시 일치 70건 그대로다. 테스트 328개 통과.

기존 시연 사진 세 장도 `scripts.compare_detector_examples`로 두 설정을 비교했다. 2017년 이마트 사진의 11개 이름과 롯데마트 사진의 3개 자동 채움은 유지되었지만, 긴 2023년 영수증에서는 어묵·가지·떡볶이떡이 빠지고 대파·양상추가 추가되었다. 전체 수량 개선만으로 이 이름 퇴행을 무시하지 않는다. 운영에는 달걀 분류 수정을 반영하고 검출 크기 기본값은 0을 유지한다.

## 타일 검출 및 부분 재인식 실험

`--profiles tiles900`으로 높이 900, 여백 100의 겹치는 영역을 비교했다. 중심 좌표에 따라 영역 소유권을 정해 동일한 상품이 별도 행에 있을 때 텍스트만으로 중복 제거하지 않는다. 경계 검출 흔들림에 대한 추가 검증이 필요하며 운영에는 연결하지 않았다.

세 사진 수량 일치는 기본 합계 14건에 비해 타일 11건, 이름·수량 동시 일치는 12건 대비 9건이었다. 타일 추론은 약 5.1~6.6초로 장변 960의 이점도 잃었다. 이 방식은 채택하지 않는다.

`scripts.experiment_name_recognition`은 미분류 상품의 텍스트 영역을 한국어 인식기에 배치로 재입력했다. 검출 없는 재인식 비용은 약 0.07~0.35초였지만 결과가 그대로이거나 악화됐다. 높은 인식 점수의 잘못된 변형도 있어 점수만으로 원문을 교체하지 않는다. 금액 영역을 포함하는 잘못 병합된 상품 행과 결제 안내가 후보로 들어간 사례도 발견되어 선택 기준 자체의 개선이 필요하다. 결과는 `output/new_receipts/name_recognition_experiment.json`에 보존한다.

이미 `감자칩사워크림`, `사과잼`으로 정확히 읽은 결과가 미분류되는 별도 문제가 확인되어 명시적 가공품 정체성 연결을 보완했다. 감자칩 소스·사과잼 쿠키를 해당 단일 품목으로 오인하지 않는 테스트를 포함한다. 테스트 341개 통과. 재인식 및 타일 기능은 여전히 실험용이다.

## 숫자 보충 비교

`scripts.evaluate_numeric_fusion`은 이미 저장된 두 검출 결과만 사용한다. 새 OCR 호출이나 운영 설정 변경은 하지 않는다.

숫자 상자만 추가하는 첫 방식은 명시적 표 머리글·열 위치·원본 상자와 충돌 없음이 필요하다. 기존 98장 수량 일치가 125→126건에 그쳐 효과가 작았다.

`--rows` 방식은 기존 상품명과 원문을 유지하고 수량만 보충한다. 기존 수량이 비어 있고, 보조 행의 단가×수량=금액이 검산되며, 이름 유사도 0.9 이상·가격 포함 관계·행 위치 일치·서로 유일한 대응을 요구한다. 이미 채운 수량 및 서로 다른 확정 식재료명은 덮어쓰지 않는다. 보조 원문과 `SECONDARY_VERIFIED_RECEIPT_COLUMNS` 출처를 별도 보존한다.

같은 98장 개발 캐시: 이름 일치 137건/이름 오류 31건 유지, 수량 일치 125→160건, 이름·수량 동시 일치 71→90건, 틀린 수량 채움 1건 유지. 결과는 `output/receipt_readiness/count_fusion.json`. 이는 독립 평가도, 전체 API 속도 측정도 아니다.

운영 도입 전 남은 검증: 새 9장과 시연 사진 재검증, 실제 2회 OCR 지연 및 필요한 경우만 실행하는 기준, 원본 숫자와 보조 숫자가 충돌하는 경우의 확인 안내. 숫자/행 보충 모두 운영에 연결하지 않았다. 테스트 357개 통과.

## 새 9장 수량 보충 검증 및 응답 정합성

새 개발용 9장에서도 검증했다(`evaluate_numeric_fusion --rows --new-development`). 식품 29행에서 수량 일치 14→15건, 이름·수량 동시 일치 12→13건, 이름 일치 21건 및 잘못 채운 수량 0건 유지. 기존 98장만큼 이득이 크지 않으므로 보조 OCR 전체 실행을 운영 기본값으로 채택하지 않는다. 고정 평가용 30장은 여전히 미사용이다.

검증 중 재고 후보 API의 `quantity_source` 허용 목록에 `RECONSTRUCTED_PRICE_COLUMNS`가 없어 실제 복원 결과 응답 검증이 실패할 수 있음을 발견했다. 해당 출처와 실험용 `SECONDARY_VERIFIED_RECEIPT_COLUMNS`를 응답 모델에 추가했다. 보조 OCR 수량에는 별도 확인 경고와 review_notes를 제공한다. 일반 영수증 응답의 필드 구조는 바꾸지 않았다.

실제 FastAPI 라우트에 OCR 상자를 주입한 테스트에서 `/ocr/inventory-candidates`가 복원 수량 2와 출처를 HTTP 200으로 반환하는 것을 검증했다. 전체 테스트 359개 통과. 보조 OCR 실행 자체는 운영 경로에 여전히 연결하지 않는다.

## 11장 확장 및 조건부 수량 보충

추가 두 장(IMG00051, IMG00287)의 max960 OCR을 수집했다. 각 추론은 약 1.96초, 2.44초였으나 별도 프로세스의 단회 측정이며 전체 API 지연을 의미하지 않는다.

동일 보조 행이 이미 수량이 있는 주행과도 대응되면, 수량 없는 중복/겹침 행에 재사용하지 않도록 일대일 검사 범위를 넓혔다. bool/NaN/무한대/범위 밖 수량 및 면적 없는 위치 정보도 거부한다. 이름·원문·이미 채운 수량은 변경하지 않는다.

조건부 실험은 `evaluate_numeric_fusion --rows --gated`이며 신규 자료에는 `--new-development`를 추가한다. 이름과 식품 분류, 가격 증거가 있고 수량이 빈 상품이 있을 때만 보조 분석을 사용한다. 이는 현재 캐시 재생 실험이며 운영에서 추가 OCR을 호출하지 않는다.

| 개발 표본 | 기본 이름·수량 동시 일치 | 조건부 보충 후 | 보조 분석 대상 | 기본/보충 구매 수량 일치 |
|---|---:|---:|---:|---:|
| 기존 98장 | 71/303 | 90/303 | 37/98장 | 125/311 → 156/311 |
| 신규 11장 | 14/33 | 17/33 | 4/11장 | 20/39 → 23/39 |

전체 이미지에 보조 분석을 수행하면 구매 수량 일치는 각각 160, 24건이지만 이름·수량 동시 일치는 조건부 방식과 같다. 이름 일치/오류는 변경되지 않았고 잘못 채운 수량도 기존 1건, 신규 0건으로 유지됐다. 기존 자료는 학습·튜닝에 사용된 데이터이며 신규 주석 역시 AI 초안이다. 독립 정확도로 발표하지 않는다.

결과 파일: `output/receipt_readiness/gated_count_fusion.json`, `gated_new_count_fusion.json`. 전체 테스트 386개 통과. 실제 조건부 2회 OCR 지연, 시연 사진 회귀, 원문 숫자 충돌 검증은 여전히 남아 있어 운영 기본값은 변경하지 않았다.

## 실제 순차 실행 시간과 시연 사진 검증

`python -m scripts.benchmark_conditional_receipt_ocr --repeats 2`로 신규 개발용 IMG00014/00051/00287과 기존 시연 사진 세 장을 각각 초기 1회+반복 2회 처리했다. 운영 서버를 변경하지 않는 별도 프로세스이며 이미지 디코딩, 기본 OCR, 분류/응답 매핑, 필요한 경우 보조 OCR 및 재매핑을 순차 실행했다. 모델 로딩은 측정에서 제외했고 HTTP/업로드/서버 대기열은 포함하지 않는다.

- 반복 12회: 기본 처리 중앙값 4.16초, 보조 처리를 포함한 중앙값 4.61초, 표본 p95 6.49초.
- 반복 중 보조 실행 4회. 해당 사진의 추가 시간은 약 1.84~2.45초다. 작은 로컬 표본이므로 운영 SLA나 실제 HTTP p95로 발표하지 않는다.
- IMG00051의 바나나 1, 미고랭누들 2 및 2017 이마트 사진의 비피더스 상품 구매 수량 1이 복원됐다. 상품 내부 12입을 구매 개수로 바꾸지 않는다.
- 세 시연 사진 및 세 신규 사진에서 기본 분류 정보와 이미 확정된 수량은 모두 유지됐다. 이는 정답 정확도 증명이 아니라 보충 전후 보존 검사다.
- 앞선 11장 캐시 실험과 대상 사진 구성이 다르다. 같은 사진에서 전처리 차이가 확인된 것은 아니다.
- 보고서: `output/receipt_readiness/conditional_ocr_benchmark.json`, 초기/반복별 시간과 보조 원문, 전후 응답을 보존한다.

기본 OCR에서 단가/숫자/금액 형태의 수량 숫자가 읽혔으나 검산에 실패한 경우, 보조 숫자가 다르면 복원을 거부하도록 추가했다. 예: 기본 `2,000 3 4,000`에 보조 `2,000 2 4,000`이 있어도 자동으로 2를 쓰지 않는다. `]` 같은 비숫자 오독을 보완할 때에는 기존 보조 OCR 출처/확인 안내가 필요하다. 전체 테스트 389개 통과. 조건부 보조 실행은 아직 운영에 연결하지 않았다.

충돌 차단 후 캐시 재검증: 신규 11장의 수량 일치 23, 이름·수량 동시 일치 17은 유지됐다. 기존 98장의 수량 일치는 156→149, 동시 일치는 90→84로 감소했다(기본 처리 대비 각각 +24, +13). 초안 정답 기준으로 맞았던 보조 숫자도 원문과 충돌하면 확인 대상으로 남긴 결과다. 잘못 확정한 수량은 기존 1건 그대로다. 무조건 차단으로 잃는 복원을 향후 확인 가능한 후보로 제공하는 방안은 별도 검토하되, 현재 수치를 과거 90건과 혼용하지 않는다. 위 시간 실험은 이 추가 차단 이전에 실행됐으며 세 복원 사례에는 서로 다른 숫자 충돌이 없었다.

## 선택적 API 연결

`OCR_SECONDARY_COUNTS_ENABLED=true`이면 `/ocr`, `/api/ocr/receipt`에서만 조건부 보조 처리를 수행한다. 기본값 false. `/ocr/raw`와 재고 후보/저장 경로는 변경하지 않는다. 기본 검출 설정 자체가 960이면 동일 설정 재시도는 생략한다. 요청별 사진은 다시 읽되 용량·형식 검사를 유지하고, 모델 추론은 기존 전역 잠금을 공유한다. 보조 처리 오류는 기록하고 기본 결과를 반환한다. 보조 출처와 사용자 확인 문구를 유지한다.

별도 로컬 서버 8011에서 실제 IMG00051 요청을 실행했다. HTTP 200, 바나나 1개·또띠아 960g(320g×3)·미고랭누들 2개, 붉은볼락은 확인 후보로 반환됐다. 최초 요청 11.78초(모델 로딩 5.263초 포함), 같은 요청 재실행 6.44초. 단일 사진 2회이므로 운영 p95가 아니다. 테스트 서버는 종료했으며 기존 8000 서버와 실제 `.env`는 변경하지 않았다.

기능 비활성화, 수량 완성, 보조 실패, raw 경로 제외, 두 영수증 라우트의 복원 및 확인 안내를 포함하여 전체 테스트 395개 통과. 실행 중 운영 서버에서 기능을 활성화한 상태는 아직 아니다.
